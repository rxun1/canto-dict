Plan 1 — Data pipeline

For agentic workers: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Task status lives in dashboard/progress.js.

Goal: one command (npm run data:build) that downloads every source, merges it, validates it and writes assets/canto.db, assets/syllables.pack, assets/syllables.json and data-pipeline/build-report.html.

Architecture: a standalone Node/TypeScript project in data-pipeline/. One module per source (download + parse) feeds a merge step that produces a single in-memory entry model; build steps write SQLite and the audio pack. Shared Jyutping logic lives in src/jyutping/ so the app reuses it.

Tech stack: Node 22, TypeScript, tsx, vitest, better-sqlite3, opencc-js, yaml, ffmpeg.

Spec sections: §4 (data pipeline), §7 (pipeline failures), §8 (pipeline tests).

Prerequisites

  • Node 22 (installed: v22.22.2).
  • ffmpeg + ffprobe (brew install ffmpeg) — checked in P1-T15.
  • The words.hk full dump, requested by hand at words.hk/faiman/request_data/ — needed by P1-T8.

File structure

data-pipeline/
  package.json, tsconfig.json, vitest.config.ts
  src/cli.ts                 step runner: download → parse → merge → validate → build (build also writes the report)
  src/download.ts            fetchToCache + manual-file overrides
  src/yaleToJyutping.ts      Yale → Jyutping (Kaifangcidian)
  src/sources/*.ts           one file per source
  src/merge/types.ts         Entry model (mirrors canto.db schema)
  src/merge/merge.ts         OpenCC normalization, reading ranks, joins
  src/validate.ts            thresholds + Jyutping validity
  src/build/schema.sql       canto.db schema (spec §4.3)
  src/build/writeDb.ts       SQLite writer
  src/build/searchKeys.ts    toned / toneless / joined keys
  src/build/audioPack.ts     syllables.pack + syllables.json
  src/build/report.ts        build-report.html
  fixtures/                  small real samples of every source
  test/                      vitest tests
src/jyutping/syllables.ts    shared syllable inventory + parser (used by the app too)
assets/test/canto.fixture.db small DB built from fixtures, committed, used by app tests

Order and dependencies

  • P1-T1 → P1-T2 → P1-T3 first (scaffold, syllables, download).
  • Source tasks P1-T4 … P1-T11 (P1-T12, the English source, was dropped with English) are independent of each other and can run in parallel.
  • P1-T13 (merge) needs all sources; P1-T14 – P1-T16 need merge; P1-T17 is last.

Risks

  • words.hk dump is a manual request → P1-T3 supports a local-file override.
  • Kaifangcidian current zip may be blocked by the corporate proxy (as during research) → download from a non-corporate network or use the override.
  • Wiktionary Lua module dump format may differ from the single-module fixture → P1-T10 DoD requires ≥ 2,000 parsed tables from the real dump.

Conventions (all plans)

  • Test-first. Every code task follows: write the failing test → run it and see it fail → write the minimal code → run it and see it pass → commit. The subtasks spell these steps out.
  • A task is done only when every item in its Definition of done holds and its How to test check passes. Run the check; don't assume.
  • Commits: one commit per task, message <task id>: <what changed>, e.g. P1-T4: parse rime-cantonese char.csv. Never push without asking.
  • Dashboard: when starting a task set its status to "doing" in dashboard/progress.js; bump progress as subtasks finish; set "done" and add a log line when the DoD is met.
  • Docs are HTML, not markdown (including generated reports).
  • Fixtures: parser tests run against small real samples saved in data-pipeline/fixtures/, never against made-up formats.
