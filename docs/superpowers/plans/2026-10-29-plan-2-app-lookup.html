Plan 2 — App shell + lookup

For agentic workers: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Task status lives in dashboard/progress.js.

Goal: an iPhone app you can install that looks up any Cantonese character or word offline — by 字 or Jyutping — shows readings, Mandarin meaning, definitions and examples, plays real-person syllable audio, and keeps favorites and history.

Architecture: Expo dev build with Expo Router tabs. Screens are thin; logic lives in src/ modules behind small interfaces. The dictionary is the read-only canto.db from Plan 1; user data is a separate writable user.db. Tests run in Jest on the Mac against assets/test/canto.fixture.db through a better-sqlite3 adapter.

Tech stack: Expo (current SDK), TypeScript, Expo Router, expo-sqlite, expo-audio, expo-file-system, Jest (jest-expo), React Native Testing Library, better-sqlite3 (tests only).

Spec sections: §3 (layout), §5 (lookup), §7 (errors), §8 (testing).

Prerequisites

  • Plan 1 done: assets/canto.db, assets/syllables.pack, assets/syllables.json, assets/test/canto.fixture.db.
  • Xcode (installed: 26.1.1) and an Apple ID for signing; iPhone with a USB cable for P2-T12.

Order and dependencies

  • P2-T1 → P2-T2 (spike) first: the spike decides whether to-jyutping and opencc-js work on device before anything depends on them.
  • P2-T3 before every data-reading task. P2-T4 → P2-T5 → P2-T6. P2-T7 needs P2-T3.
  • P2-T8 and P2-T9 are independent; P2-T10 needs P2-T9; P2-T12 is last.

Conventions (all plans)

  • Test-first. Every code task follows: write the failing test → run it and see it fail → write the minimal code → run it and see it pass → commit. The subtasks spell these steps out.
  • A task is done only when every item in its Definition of done holds and its How to test check passes. Run the check; don't assume.
  • Commits: one commit per task, message <task id>: <what changed>, e.g. P1-T4: parse rime-cantonese char.csv. Never push without asking.
  • Dashboard: when starting a task set its status to "doing" in dashboard/progress.js; bump progress as subtasks finish; set "done" and add a log line when the DoD is met.
  • Docs are HTML, not markdown (including generated reports).
  • Fixtures: parser tests run against small real samples saved in data-pipeline/fixtures/, never against made-up formats.
